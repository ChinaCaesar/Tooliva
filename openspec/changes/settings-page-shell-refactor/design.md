## 背景与现状

应用已具备首页仪表盘式信息架构（顶栏、侧栏卡片、底栏等）与独立的 `SettingsPage`，后者当前依赖 `ToolPageTopBar` 与纵向简单分区，与设计稿中的「侧栏加顶栏搜索加双列卡片设置」不一致。设计稿强调壳层与内容解耦，以便多页面复用同一导航与窗口操作习惯。

## 目标与非目标

**目标：**

- 将侧栏、顶栏、底栏抽取为可组合的应用壳层，使设置页与首页在导航与全局控件上体验一致。
- 设置主内容按卡片分组呈现，控件形态与设计稿对齐（开关、选择器、分段按钮、路径行、危险操作按钮、关于区块）。
- 通过配置或轻量组合组件降低设置项增删时的重复模板代码。

**非目标：**

- 不要求在本变更中一次性实现设计稿上全部与 Tauri 或操作系统深度耦合的能力（例如真实开机自启、托盘常驻），若尚无后端支撑，以 UI 与 store 字段预留或功能开关隐藏为限，并在任务中单独标注。
- 不重构业务工具页内部的 `ToolPageTopBar` 语义，除非为共享壳层让路且验收明确包含。

## 技术决策

1. **壳层放置位置与命名**  
   在 `src` 下新增应用布局目录（例如 `src/layouts/app-shell/` 或 `src/components/app-shell/`），导出 `AppSidebar`、`AppHeader`、`AppFooter`、`AppShellLayout`（或等价命名）。首页与设置页通过同一 `AppShellLayout` 包裹，仅替换默认插槽内子路由或页面级组件，避免复制粘贴侧栏 markup。

2. **首页与设置的迁移顺序**  
   先将壳层从首页抽取为独立组件（侧栏与顶栏若已在 `HomePage` 内联，则迁移至壳层），再让 `SettingsPage` 使用该壳层；这样可尽早验证侧栏在多条路由下的高亮与滚动行为。

3. **设置分区实现**  
   采用「卡片容器加设置行」二级结构：`SettingsSectionCard` 包裹标题与描述；`SettingsRow` 接收标题、说明文案插槽或 prop、以及右侧控件插槽。复杂区块（关于、路径行）拆为独立小组件，避免单文件过长。

4. **状态与持久化**  
   已有项（语言、窗口尺寸、任务完成提醒等）继续经 `useSettingsStore` 读写；新增项在同一 store 中扩展并沿用现有持久化策略（如 localStorage 或 Tauri 插件），键名带版本前缀或命名空间以防冲突。

5. **样式与令牌**  
   复用首页已用的颜色、圆角与间距变量（若项目使用 CSS 变量或设计令牌则引用之；否则从 `HomePage` 与相关组件复制基准值并在壳层集中定义，避免魔法数散落）。

6. **i18n**  
   所有新增可见文案走 `vue-i18n`，键名按 `pages.settings.*` 或 `layout.appShell.*` 分层，中英文同步占位。

## 风险与权衡

| 风险 | 缓解措施 |
| --- | --- |
| 抽取壳层后首页回归工作量大 | 分步提交：先抽组件不改行为，再改设置页路由布局；对照设计稿做关键路径手测。 |
| 侧栏数据与首页 mock 强耦合 | 将导航项配置提升到 `home.config` 同级或新建 `appNav.config.ts`，由壳层只依赖配置与路由元信息。 |
| 设计项超出现有能力导致范围膨胀 | 提案与非目标已约束；任务单中为每项标「需 Tauri」或「仅 UI」。 |

## 迁移与发布

- 默认无破坏性 API 变更；若调整路由嵌套，需保证对外深链到 `/settings` 的路径仍可用。
- 回滚策略：保留旧 `SettingsPage` 布局分支或 Git 回退即可，不涉及数据库迁移。

## 待解决问题

- 侧栏「更多工具」展开行为是否与首页当前交互完全一致，由产品确认后固化到规格。
- 搜索框在设置页是否复用首页同一数据源与快捷键（Ctrl K），需在实现前确认与全局快捷键注册是否冲突。
